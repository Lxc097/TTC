# 招聘流程与状态机

这份文档回答四个问题：**候选人处在哪一步**、**谁能把它推进到下一步**、**每一步两端分别能看到什么**、**代码改哪里**。

对应 issue：[#4 企业端招聘管理界面](https://github.com/Lxc097/TTC/issues/4)、[#5 候选人端按阶段展示状态](https://github.com/Lxc097/TTC/issues/5)。本文件描述的是后端地基（PR1）；企业端工作台与候选人阶段页在前端 PR 接入，接口与字段以本文为准。

## 一、四个阶段

| 阶段 | 含义 | `applications.status` | 推进者 | 候选人的「下一步」 |
|---|---|---|---|---|
| 1 投递与初筛 | 简历已提交，等待解析与内部初筛 | `submitted`、`parsing`、`screening`、`hr_review`、`failed` | 候选人投递、后台初筛 | 等待企业审核 |
| 2 AI 初面 | 已获邀请，可进入正式 AI 初面 | `ai_interview_invited`、`ai_interview_in_progress`、`ai_interview_completed` | HR 邀请、候选人进入并完成 | 在截止时间前进入 AI 初面 |
| 3 真人面试 | 企业已安排真人面试 | `hr_interview_invited` | HR 安排 / 改期 | 按约定时间进入面试房间 |
| 结束 | 已出结论，流程结束 | `closed` | HR 提交真人面试结论 | 查看（已发送的）结果 |

规则：

1. **候选人只看当前阶段**。DTO 返回 `stage` 与 `stageLabel`，不返回后续阶段的时间线或内容。
2. **只能前进**。已进入阶段 3 或已结束的申请，不会被迟到的初筛结果、AI 房间结束事件改写回阶段 1/2。
3. `pipeline.stage_of()` 是唯一映射；任何页面都不允许自己再写一份 if/else。

## 二、两种邀请的状态机

两种邀请都不新增「状态列」，展示状态在**读取时**计算（`expires_at` 一到就显示已过期，不依赖定时任务）。

### AI 初面邀请（`invitations`，一申请一条）

| 展示状态 | 判定 |
|---|---|
| 待响应 | `status=invited` 且未过期、未接受 |
| 已接受 | `status=in_progress` 或已有 `accepted_at` |
| 已过期 | `status=invited` 且 `now >= expires_at` |
| 已完成 | `status=completed` |

- 有效期默认 7 天（`AI_INVITE_DAYS`）。
- 重发只更新 `sent_at` / `last_sent_at` / `send_count` 并顺延 `expires_at`，**不会**产生第二条记录。
- 候选人已进入面试或已完成时不能重发。

### 真人面试邀请（`human_interviews`，一申请一条）

| 展示状态 | 判定 |
|---|---|
| 待响应 | 已安排、未接受、未过期 |
| 已接受 | 候选人点过「进入面试房间」，记录 `accepted_at` |
| 已过期 | 超过 `expires_at` 仍未完成 |
| 已完成 | 已写 `result` |

- 有效期默认「面试时间 + 3 天」（`HUMAN_INVITE_DAYS`），用于「面试后多久还能进房间/补面」。
- `video` 形式复用该申请的同一间双人面试间（按申请幂等，不新建第二间房）；`onsite` / `phone` 只记录地点或联系方式。

## 三、两端各能看到什么

### 企业端（HR，按企业隔离）

| 字段 | 说明 |
|---|---|
| `stage` / `stageLabel` | 该申请当前阶段 |
| `invitation.state / sentAt / expiresAt / sendCount` | AI 初面邀请的状态与时间 |
| `humanInterview`（含 `notes`、`result`、`resultSent`） | 真人面试安排与内部结论 |
| `interviewRoomReport`（详情） | 归档的双人面试间报告（双确认、追问点） |
| `aiResultSent` | AI 初面结果是否已发给候选人 |

### 候选人端

| 字段 | 说明 |
|---|---|
| `stage` / `stageLabel` | 只表示当前阶段 |
| `invitation.state / expiresAt / interviewPath` | 阶段 2 的时间与入口 |
| `humanInterview.state / scheduledAt / interviewerName / mode / location / roomCode / enterable` | 阶段 3 的安排；**不含** `notes` |
| `result` | 仅当 `resultSent=true`：`{visible, conclusion, message}` 一句话结论 |
| `aiResult` | 仅表示企业是否已发送 AI 初面结果；不含分析内容 |

**永远不进入候选人 DTO 的字段**：`screening` 报告、`matchScore`、`review`（审核意见）、`formalInterview.analysis`、`humanInterview.notes`、面试间报告。

## 四、接口

### 企业端

| 方法 | 路径 | 说明 |
|---|---|---|
| PUT | `/api/hr/jobs/{job_id}/criteria` | 保存 HR 自写初筛标准（≤4000 字，仅本企业可见） |
| GET | `/api/hr/applications?stage=applied\|ai_interview\|human_interview\|ended` | 按阶段过滤 |
| POST | `/api/hr/applications/{id}/human-interview` | 安排真人面试 |
| PATCH | `/api/hr/applications/{id}/human-interview` | 改期 / 提交结论 / 切换结果可见性 |
| POST | `/api/hr/applications/{id}/human-interview/resend` | 重发真人面试邀请 |
| POST | `/api/hr/applications/{id}/invitation/resend` | 重发 AI 初面邀请 |
| POST | `/api/hr/applications/{id}/ai-result/send` | AI 初面结果是否发送给候选人 |
| GET | `/api/hr/invitations?kind=ai\|human&state=` | 邀请记录（两种邀请合并，含计数） |
| GET | `/api/hr/applications/{id}/interview-room` | 归档的面试间报告 |

### 候选人端

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/applications/my`、`/api/applications/{id}` | 阶段、邀请与结果字段 |
| POST | `/api/applications/{id}/human-interview/enter` | 进入真人面试房间（返回房间号与本人票据） |

## 五、初筛标准如何生效

HR 写的标准保存在 `jobs.screening_criteria`，随初筛任务作为「评估维度」进入模型请求：

- 位置：`screen_resume(parsed, job, evidence, criteria=...)` 的 user message；
- 边界：提示词明确写了它**不是指令**、不得改变输出结构、评分规则与安全约束；长度截断到 4000 字；
- 无标准时请求体与旧版完全一致；
- 提示词版本升到 `resume-screening-2026-11-v4`（版本号会写进 `screenings.prompt_version`，便于回溯）。

## 六、数据与环境变量

迁移全部是加法，旧库启动时自动补齐：

| 位置 | 新增 |
|---|---|
| `jobs` | `screening_criteria`、`criteria_updated_at` |
| `invitations` | `sent_at`、`expires_at`、`accepted_at`、`send_count`、`last_sent_at`、`result_sent` |
| `human_interviews`（新表） | 一申请一条：安排、结论、可见性、计数 |
| `interview_reports`（新表） | 面试间报告归档（`session_id` + `report_json`） |

两张新表都对 `applications(id)` 设 `ON DELETE CASCADE`，随 `RECRUITMENT_RETENTION_DAYS` 的保留期清理。

| 变量 | 默认 | 说明 |
|---|---|---|
| `AI_INVITE_DAYS` | 7 | AI 初面邀请有效期（天） |
| `HUMAN_INVITE_DAYS` | 3 | 真人面试邀请在面试时间之后的有效期（天） |

## 七、合规口径（不要为了「好看」破例）

1. **不把生理信号塞进 AI 初面**。正式 AI 初面在代码里就是 `formal` 模式，默认不采集画面信号；「生理 ∧ 行为双确认」只属于双人面试间，展示时必须标注来源。
2. **不给候选人打分或排名**。候选人端只有「结论一句话」；企业端的指标条只放过程与证据类数据（题数、逐题证据分布、取证请求/坐实数、提示采纳率），不放总分与人格/诚信判断。
3. **结果发送开关只控制可见性**，不改变内部记录；关闭后候选人回到「等待企业通知」。
4. **AI 不做录用决定**。所有推进动作（邀请、安排、结论）都必须由 HR 显式触发。

## 九、企业端页面（PR2）

四个页面都挂在 `/classic/` 下，共用 `frontend/interviewer/recruitment-core.js`（鉴权、同源接口、导航、弹窗、下载原简历）与 `workspace.css`。只有 `screening.html` 承担登录，其余页面未登录会跳回登录页。

| 页面 | 路径 | 做什么 |
|---|---|---|
| 查看简历 | `/classic/screening.html` | 子页签「筛选后的简历 / AI 初筛标准」；卡片翻页（发送邀请 / 跳过）与列表展开；岗位发布、PDF 录入、完整详情 |
| AI 面试结果 | `/classic/ai-results.html` | 初面列表与逐题证据、指标条、双确认佐证（有归档时）、进入真人面试、结果发送开关 |
| 真人面试结果 | `/classic/human-results.html` | 安排/改期、填写结论与内部备注、结果发送、查看双人面试间归档 |
| 邀请记录 | `/classic/invites.html` | AI 初面与真人面试邀请回溯、按状态筛选、重发并顺延有效期 |

卡片翻页的「跳过」映射为 `hold`（暂缓），不是淘汰；企业录入（`hr_import`）的简历沿用旧规则，不能发送线上邀请。候选人阶段页（issue #5）在 PR3 接入，复用同一套接口。
