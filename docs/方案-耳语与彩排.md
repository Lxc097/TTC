# 耳语 / 彩排 · 面试双方各自的镜子

> TTC「AI 赋能招聘与人才挖掘」黑客松 · 方案 v2（双边版）

---

## 0. 一句话

**同一份心跳，面试官听到的是「该往哪问」，候选人听到的是「该往哪改」——我们从不说这个人好不好。**

- 给面试官的产品叫 **「耳语」**：面试中的耳边助教，只递追问建议。
- 给候选人的产品叫 **「彩排」**：面试前的表达体检，只给改进方向。
- 底下是**同一个认知负荷引擎**，两个视图，两种情感方向。

---

## 1. 定位与边界（这一节决定项目生死）

| | 做 | 不做 |
|---|---|---|
| 输出（面试官侧） | 1–3 条追问建议 + 面试质量报告 | 候选人分数、排名、淘汰建议 |
| 输出（候选人侧） | 表达改进建议 + 自己的曲线回放 | 给候选人打的「表现分」 |
| 主体 | 面试官（真人）／候选人本人 | 平台方、第三方 |
| 信号 | 「认知负荷」相对变化 | 「情绪」标签、测谎结论 |
| 留存 | 本人可删除，不留生物特征库 | 跨会话建立候选人画像 |

**四条铁律，写在 PPT 里也写在代码注释里：**

1. **信号永不展示给候选人对面的第三方**——候选人自己的数据只有他自己能看到完整版。
2. **不产生任何自动决策**，系统只递建议，判定权 100% 在人。
3. **不做情绪标签**。估计的是 *cognitive load（认知负荷）*，不是 emotion。
4. **两边都不出「这个人行不行」的结论。** 面试官得到的是「这里还有东西没挖」，候选人得到的是「这里还没练熟」。

## 2. 核心机制：把生理信号翻译成两边都听得懂的话

### 2.1 面试官侧：三个决策

面试官在 45 分钟里同时干三件事：听内容、判深度、管节奏。他真正需要的只有三个答案：

| 面试官的内心问题 | 系统信号 | 提示文案（≤10 字） |
|---|---|---|
| **这段还有料没挖出来？** | 负荷突升 + 语义回避（模糊词、被动句、时间跳跃） | 「追问：具体卡在哪」 |
| **题是不是太浅了？** | 整题负荷低 + 回答流利且短 | 「升级难度」 |
| **他是不是到极限了？** | 连续高负荷 + 语速下降 + 答句变短 + 呼吸变浅 | 「收，换轻松话题」 |

### 2.2 候选人侧：三条真正有用的建议

候选人侧最容易做错——**给一个「紧张指数 78 分」就毁了这个产品**。正确形态是 coach，不是 judge。文案要具体到能直接改行为：

- 「这段 235 字/分钟、几乎没有停顿。面试官想追问也插不进嘴——**留白比多说有力**。」
- 「第 3 题之后句长掉了 40%、呼吸变浅。这是你的**注意力拐点**：真实面试前 25 分钟决定印象，把最想讲的放前面。」
- 「这题负荷比你自己基线高 2.1 个标准差，但内容质量是全场最高的——**不是你不懂，是这段还没练熟**。再讲两遍就顺了。」
- 「讲离职原因时视线离屏率 62%，面试官几乎一定会注意到。建议提前把这段结构成一二三。」

**注意最后一条的温度**：别人给分数让人焦虑，我们给原因让人松一口气。这就是差异化。

### 2.3 为什么「认知负荷」是唯一正确的构念

- 有公开研究基础：认知负荷与心率、心率变异性、呼吸频率、瞳孔直径相关。
- 不需要判断「他是不是在说谎」——**编造和回忆都会加载，只是加载方式不同**，所以只提示「这里有东西」，不判断「这里有问题」。
- 不构成 EU AI Act 第 5(1)(f) 所禁止的「工作场所情绪识别」，也不触发 PIPL「自动化决策」的强监管。

## 3. 双边结构：一个引擎，两个视图（这一节是商业模式的全部）

```
                 认知负荷引擎（同一套特征、同一套规则）
                    │                         │
        ┌───────────┴───────────┐   ┌─────────┴────────────┐
        │  面试官视图「耳语」    │   │  候选人视图「彩排」    │
        │  · 沉默色带 + 6 字提示 │   │  · 自己的曲线回放      │
        │  · 面试质量报告        │   │  · 可执行的表达建议    │
        │  · 看不到完整生理曲线  │   │  · 报告归本人，可删可导出│
        └───────────────────────┘   └──────────────────────┘
                    │                         │
                    └──── 可携带的同意 ────────┘
                          （本人授权的最小单元）
```

### 3.1 为什么需要双边，不是善意，是必然

1. **B 端最大的阻力不是技术，是「候选人愿不愿意被分析」。** 单边 to HR 的产品，候选人一律视为监控，对抗性紧张会污染基线数据。
2. **C 端先给价值，才有授权。** 候选人在「彩排」里先得到了一份确实有用的表达体检，他才会愿意把信号授权给某一场真实面试。**先给价值、再要授权，是唯一能规模化的同意模式。**
3. **C 端是免费获客入口。** 每场真实面试的计费在 B 端，获客成本在 C 端——这是标准的双边市场结构。

### 3.2 「可携带的同意」——本项目真正的护城河

- **最小授权单元**：不是「同意被分析」，而是「同意本次会话的 3 条追问建议被这位面试官看到」。可撤销、可见范围、有时限。
- **数据归属**：候选人的完整曲线永远只属于他本人；面试官侧只拿到压缩后的建议，拿不到原始生理序列。
- **反直觉但关键的一点**：**自愿授权会提高信号质量。** 被迫监考下候选人处于对抗性紧张，基线被污染；自愿授权下他更放松，负荷曲线更干净。
  > **所以合规不是我们的成本，是我们的数据质量优势。** 这句话请放在 PPT 上。

### 3.3 双边带来的额外好处

评委席里如果有 C 端/消费级背景的人，候选人侧能救你——否则 to HR 的故事容易被判为「一个功能」。双边市场写进商业模式页，估值逻辑立刻不一样。

## 4. 信号与算法

### 4.1 基线：唯一能让数据说人话的办法

摄像头 rPPG 的绝对值不可信（光照、压缩、肤色、个体差异）。**永远不看绝对值，只看相对自己基线的偏离。**

- 面试前 60 秒（寒暄/等待/自我介绍前）自动建立基线：静息 HR、呼吸频率、眨眼率、语速。
- 之后所有输出都是 **z-score（偏离自己基线几个标准差）**。

> 答辩台词：「我们不判断你紧张不紧张，我们判断**你这一段比你自己刚才更费力**。」

### 4.2 双确认机制（防误报，也是最好的技术答辩点）

**只有生理信号和行为信号同时异常，才允许出提示。**

```
提示 = (生理偏离 z > θ₁) AND (行为异常 ∈ {停顿时长↑, 填充词密度↑, 语速↓, 视线离屏率↑})
```

单一信号一律静默。这一步能砍掉绝大部分误报，评委会立刻认可你「知道自己的信号有多脏」。

### 4.3 具体特征集（务实版，按可靠性排序）

| 特征 | 可靠性 | 说明 |
|---|---|---|
| HR 斜率（回答内 15–20s 窗口滑动） | 高 | ±5 bpm 即可用，趋势比绝对值重要 |
| HR 恢复时间（回答结束后 20s 内回落速度） | 高 | 很好的负荷代理，且比绝对值稳 |
| 呼吸频率变化（变浅/变快） | 中 | 30s 窗口，可作辅助 |
| HRV / RMSSD | 低 | **只看趋势，别报数字**，主动承认噪声 |
| 行为侧：停顿、填充词、语速、视线 | 高 | 用它们给生理信号兜底 |

> 每个特征带一个 `confidence`，低置信度直接丢弃。**宁可漏报，不可误报**——面试官被坑一次就不用了；候选人被吓一次就不敢再练了。

## 5. 实时性：必须现在就打破的一个误区

**「逐秒实时」是伪需求。**

面试官在候选人说话时，本来就不该低头看屏幕——盯着提示看会漏掉内容，这是反人性的。所以正确的形态是：

> **候选人回答结束后 3 秒内，给出这轮的建议。**

这把延迟预算从 200ms 放宽到 3000ms，**云端 API 哪怕 1–2 秒延迟也完全够用**。这是本方案对技术风险最重要的一次规避。

- **异步任务式 API**：每 20–30 秒切一个窗口跑一次，轮次结束时弹提示。叙事不变，只叫「轮次级提示」。
- **只支持整段视频**：面试中只跑基线 + 行为信号，结束后 60 秒出完整报告——Demo 就得靠预录。

**行动项：今天就去压测单次调用延迟和最长视频时长。这是唯一的技术生死线。**

## 6. Demo 脚本

### 6.1 主秀：A/B 对照（60 秒，必须预录成视频）

黑客松最有说服力的不是功能，是**因果**。

- **准备**：同一个演员，同一套问题，录两遍，剪成左右分屏。
- **A 屏（无 Copilot）**：面试官问三个常规问题，候选人把失败项目说成「后来因为公司战略调整没上线」，面试官点头，换题。**（漏了）**
- **B 屏（有 Copilot）**：同样对话，2:10 处侧边浮出一条 `⚠ 负荷突升 建议追问` → 面试官追问「你说战略调整，具体是哪一步卡住的？」→ 候选人讲出真实原因：技术债、和团队的分歧。
- **收尾字幕**：同样的候选人，Copilot 让面试官多挖出 1 个关键信息。

### 6.2 第二幕：20 秒的视图切换（双边故事的杀手锏）

紧接着，**同一段视频、同一个引擎**，把界面切到候选人视角：

> 「这是刚才那位候选人面试结束后自己看到的。他看到的是：第 3 题之后他的句长掉了 40%，建议把最想讲的放前面。**没有分数，没有排名，没有『你在第几名』。**」

20 秒，同时讲清三件事：技术是同一个、我们不重复造轮子、双边商业模型成立。**这是全项目投入产出比最高的 20 秒。**

### 6.3 现场 live（可选加分，风险自控）

请一位评委当候选人，题目选「讲一个你至今觉得遗憾的决定」——这类题必然触发负荷突升，命中率高。

- 屏幕上只显示**一条色带**，不显示任何数字（数字会让人本能质疑精度）。
- 面试官（队友）收到提示后追问。
- 关键体验：**评委亲身感受到「它注意到了我说话时的变化」**。

**保底**：给面试官准备「没触发提示时」的常规追问脚本，绝不冷场；预录视频随时可切。

### 6.4 报告形态（对应题目要求的「自动生成评估报告」）

```
面试质量报告 · 2025-XX-XX
────────────────────────
本场 3 个值得追问的点：
  02:10  失败项目未说清原因          → 建议二面追问
  08:45  技术方案深度仅到第一层       → 建议加一道设计题
  15:20  候选人明显疲劳，最后 2 题信息量低 → 建议拆两轮

本报告不包含对候选人的任何评分或排序。
```

**注意标题**：是「面试质量报告」，不是「候选人评估报告」。这个词换掉，合规风险归零，而且面试官真的会用——它帮他复盘自己的面试。

## 7. 架构与排期

```
浏览器 getUserMedia
  ├── 视频帧 5fps（降采样 320px）──→ 云端人脸/生理 API ──→ HR/RR 时间序列
  └── 音频流 ──→ TTC 实时语音接口（STT + LLM + TTS）──→ 文本 + 时间戳 + 行为特征
                                    │
                          按「问答轮次」对齐融合
                                    │
                     双确认规则引擎（生理 ∧ 行为）
                                    │
              ┌─────────────────────┴─────────────────────┐
        面试官视图（WebSocket 推一条提示）        候选人视图（回合结束刷新建议）
                                    │
                        面试结束 ──→ LLM 生成两侧报告
```

**关键实现决策：同一个前端页面 + 一个 `?role=interviewer|candidate` 开关**，组件复用，只换展示层。**不要写两套 UI**——UI 是 48 小时里最大的隐形黑洞。

技术栈：**FastAPI 单进程 + WebSocket + 原生 HTML/JS**。不要 React、数据库、登录系统。

### 排期

| 时段 | 目标 | 验收 |
|---|---|---|
| H0–4 | 视频帧 → 云端 API → 屏幕上一个数字 | 管道通，心跳能跳 |
| H4–10 | 实时语音问答闭环（能问 3 题、能打断） | 真能对话 |
| H10–18 | 基线 + z-score + 双确认规则 | 能出 1 条有意义的提示 |
| H18–24 | 面试官视图 UI + 报告 | 端到端跑通一次 |
| H24–28 | **候选人视图（复用组件，只换文案与展示）** | 20 秒切换能演 |
| H28–36 | **录 A/B 对照视频 + 排练 live** | 有 fallback |
| H36–42 | PPT（≤10 页）+ 合规一页 + 双边商业模型一页 | 能讲 3 分钟 |
| H42+ | 睡觉 | 真的去睡 |

**明确不做**：简历解析（另一个赛道）、ATS 集成、多人协作、模型训练、候选人侧历史趋势（第一版不需要账号体系）。

**砍功能的顺序**：先砍候选人侧的 live demo（保留 20 秒切换）→ 再砍 live 面试官演示（保留预录）→ 绝不砍 A/B 对照视频和合规页。

## 8. 评委问答预演

**Q：「这不就是情绪识别吗？违法吧？」**
A：「我们不做情绪标签、不产出评分、不参与任何决策。我们估计的是认知负荷的相对变化，输出里根本没有『情绪』这个字段。而且候选人侧的完整数据只属于他本人，面试官只拿到压缩后的建议。」

**Q：「准确率多少？」**
A：「我不报单点准确率，它取决于光照和姿态。我报：**在自造样本上，双确认机制把误报压到 X 次/场**。宁可漏报不可误报——面试官被误报坑一次就不用了。」

**Q：「候选人凭什么同意？」**
A：「因为他先拿到了东西。他在『彩排』里得到了一份确实有用的表达体检，然后才决定要不要把某一场面试的 3 条建议授权给面试官。**先给价值，再要授权。**」

**Q：「面试官真的会用吗？」**
A：「所以入场形态是沉默的：一条色带、六个字。他不需要学，也不需要看。」

**Q：「为什么两边都要做，不会分散吗？」**
A：「因为 B 端唯一的阻力是候选人的信任，而信任只能从 C 端给出来。我们做的是一个引擎、两个视图——代码量只多了 15%，但拿到了获客入口和同意凭证。」

**Q：「商业化？」**
A：「B 端按场次计费（接进已在收钱的视频面试/ATS 厂商），C 端免费做获客与授权网络。双边，不是两个产品。」

## 9. 供应商问询清单（今天发出去）

1. 同步 API 还是异步任务？单次调用**延迟**？能否流式/分段上传？
2. 单次支持**最长**多长视频 / 能否持续推流？
3. 最低帧率与分辨率要求？侧脸、眼镜、口罩可用性？
4. **是否返回 signal quality / 置信度字段？**（最关键，没有它做不了双确认）
5. HR / RR 的标称误差是多少？窗口多长？
6. 是否提供 HRV（RMSSD）？窗口多长？
7. 是否支持**多人脸检测**、人脸框/关键点输出？
8. 数据是否留存或用于训练？能否签 DPA？价格、配额、并发上限？

## 10. 三个必须今天验证的假设（按风险排序）

1. **延迟**：单次调用 < 3s 吗？→ 决定「轮次级提示」能不能做。
2. **信号质量**：普通笔记本摄像头 + 室内灯光下，HR 能不能稳定到 ±5bpm？→ 决定 live demo 能不能跑。
3. **可复现性**：同一个人讲同一段话两遍，负荷曲线长得像不像？→ 决定 A/B 对照视频能不能剪出来。

**任何一条挂了就立刻降级**：改用预录视频 + 行为信号（停顿/语速/视线）为主，生理信号作为「补充观察」讲。项目不会死，只是 Demo 从 live 变成 video。
