# 前端对接文档 · 耳语（企业端）

> 对接方：面试官侧页面（`index.html` / `app.js`）
> 后端：`qiyeduan/backend`（FastAPI，`uvicorn main:app --port 8000`）
> 最后核对：触发/确认链路已通过 `tools/verify_trigger_flow.py` 验证

---

## 0. 30 秒上手

```bash
cd qiyeduan/backend
pip install -r requirements.txt
set VISION_PROVIDER=mock          # 先跑 mock，不花钱
uvicorn main:app --reload --port 8000
```

- 后端自测台：<http://127.0.0.1:8000> （能看完整链路，不用你写代码）
- 录制器参考：<http://127.0.0.1:8000/recorder>
- 前端只需要连一个 WebSocket，**没有别的依赖**。

```
POST /api/rooms  →  { code: "ABC123" }
        ↓
ws://127.0.0.1:8000/ws/room/ABC123?role=interviewer
```

## 1. 两个角色，同一个端点

| 角色 | URL 参数 | 谁连 |
|---|---|---|
| 面试官 | `?role=interviewer` | 你要做的页面 |
| 候选人 | `?role=candidate&consent=1` | 候选人侧页面 |

**候选人先连上，会话才会创建**（`consent=1` 表示已授权；`consent=0` 时后端一条生理数据都不采）。

连上后第一件事是收到 `hello_ack`：

```json
{
  "type": "hello_ack", "role": "interviewer",
  "room": { "code": "ABC123", "job_title": "后端工程师", "status": "live",
            "questions": ["..."] },
  "session_id": "8d1711e2ba4a",
  "baseline_seconds": 60,
  "server_t": 1763000000.123
}
```

紧接着面试官会收到一条 `snapshot`（刷新重连时用来恢复历史提示，见 §7）。

## 2. 消息总表

### 2.1 面试官收到的（你主要处理这些）

| type | 何时来 | 你要做什么 |
|---|---|---|
| `signal` | 每采到一个生理点 | 更新信号带颜色（**不显示数字**） |
| `turn_start` | 开始一轮回答 | 轮次分隔线 |
| `turn_summary` | 一轮结束 | 可选：调试面板显示 `beh_anomaly` |
| `confirm_requested` | 行为报警、开始取证 | 提示区显一行"正在取证…" |
| `hint` | **核心** | 弹提示卡 |
| `confirm_result` | 取证回来但没坐实 | 把"正在取证"改成"未证实" |
| `hint_ack` | 你点了用掉/忽略 | 更新采纳计数 |
| `peer` | 候选人上线/掉线 | 顶部状态 |
| `status` | 降级/未授权 | 黄条 / 红条 |
| `report_ready` | 面试结束 | 跳报告页 |
| `snapshot` | 连上瞬间 | 恢复已发生的提示 |

### 2.2 你发给后端的

| 用途 | 消息 |
|---|---|
| 点「用掉」 | `{"type":"hint_feedback","hint_id":"17eaa97d","action":"used"}` |
| 点「忽略」 | `{"type":"hint_feedback","hint_id":"17eaa97d","action":"ignored"}` |
| 结束面试 | `{"type":"end"}` |
| 心跳 | `{"type":"ping","t":12.3}` |

> `end` **只有面试官能发**，候选人发了会被忽略。

### 2.4 会议纪要（语音转写）

两端各自把**自己说的话**转成文字发上来，服务端按**连接角色**标注发言人并广播给双方。

```js
// 客户端 → 服务端（边说边发，final=false 是中间结果）
{ "type": "stt", "text": "我做过三年后端", "final": true }
```

```json
// 服务端 → 双方
{ "type": "transcript", "id": "a1b2c3d4", "role": "candidate",
  "text": "我做过三年后端", "final": true, "t": 42.3 }
```

- **发言人由服务端根据连接角色判定**，客户端传 `speaker` 会被忽略——否则候选人能把面试官的话标成自己说的。
- `final=false` 只广播不落库（边说边变的中间结果不进纪要）；`final=true` 才写入时间线。
- 上限 500 条，防内存涨爆。
- 重连时 `snapshot.transcript` 会带回最近 80 条，纪要不会丢。
- 历史纪要：`GET /api/sessions/{sid}/transcript?limit=200`；报告里也带 `transcript`（最近 120 条）。

**STT 从哪来**：浏览器 `webkitSpeechRecognition`（Chrome/Edge 可用，中文 `zh-CN`）。
它不可用或识别失败时，面试官页仍可用**手打输入框**发送——所以这个功能在任何环境下都能演示。
⚠️ 两页开在同一台电脑上会有回声重复，演示时用两台设备，或只开一端。

`t`（相对会话开始的秒数）**一律由服务端生成**，客户端传的 `t` 会被覆盖。

原因是面试官和候选人各自从"自己连上那一刻"计时，两条时间轴可能差几十秒；
混用会让轮次、采样、报告时间戳全部错位。所以：

```js
ws.send(JSON.stringify({ type: "turn_start" }));   // 不带 t 也可以
```

收到的每条消息里的 `t` 都是服务端时钟，可以直接拿去做时间轴和报告。

## 3. `signal` —— 信号带怎么画

```json
{
  "type": "signal", "t": 170.0,
  "load_z": 1.83,              // 相对本人基线的偏离（σ）
  "hr": 96.4, "rr": 16.0,
  "quality": 0.45,             // sqi，0~1
  "face_count": 1,
  "baseline_ready": true,
  "baseline_remaining": 0.0,
  "signal_weak": false,        // 0.15~0.30 时为 true，要标"信号偏弱"
  "liveness": { "is_live": true, "score": 0.861, "status": "ok", "blink_rate": 1 },
  "rr_unavailable": "not_available"   // 可选，rr 缺失时才有
}
```

**渲染规则（照抄就行）**：

```js
const BAND = { idle:'#2a2a2e', blue:'#3b6ea5', amber:'#c08a3e', red:'#b3453e' };

function bandColor(m) {
  if (!m.baseline_ready) return BAND.idle;        // 基线期：灰
  if (m.quality < 0.15) return 'striped';         // 数据不可用：条纹
  if (m.load_z > 2.0) return BAND.red;
  if (m.load_z > 1.5) return BAND.amber;
  if (m.load_z > 0.8) return BAND.blue;
  return BAND.idle;
}
```

⚠️ **信号带上永远不要出现数字。** 一旦有数字，面试官就会低头去读，产品就变成了仪表盘。

基线期用 `baseline_remaining` 倒计时：`建立基线中 12s`。
`signal_weak === true` 时在角落加一行小字：**信号偏弱，仅供参考**。

## 4. `hint` —— 提示卡

```json
{
  "type": "hint", "id": "17eaa97d", "turn_id": 2,
  "kind": "probe",              // probe | upgrade | wrap
  "text": "追问：当时谁反对",     // ≤10 字，直接照着问
  "why": "负荷 +6.5σ，且停顿明显变长",
  "t": 150.0,
  "confirmed": true             // 取证确认过
}
```

`kind` 决定样式与措辞方向：

| kind | 含义 | 卡片标题 |
|---|---|---|
| `probe` | 有东西没说透 | ⚠ 追问 |
| `upgrade` | 题可能太浅 | ↑ 加难度 |
| `wrap` | 该收了 | ○ 收一下 |

**显隐规则**：
- 右侧窄栏滑入，**最多同时 2 张**，3 秒后自动淡化到 45% 不透明度（不消失、不移走）。
- 卡片上两个按钮：「用掉」→ `used`，「忽略」→ `ignored`。
- 展开后才显示 `why` 和证据。

⚠️ **三禁止**（评审会看这一条）：

```
✅ 追问：具体卡在哪        ❌ 候选人在隐瞒（结论）
✅ 升级难度：要具体数字     ❌ 技术深度不足（评价）
✅ 收，换轻松话题          ❌ 建议淘汰（决策）
```

## 5. `confirm_requested` / `confirm_result` —— 取证过程

行为信号报警时，后端会花 17 万 token 采一段视频去确认。**这中间有 30~40 秒**，界面必须让面试官知道"系统正在取证"，否则他会以为卡住了。

```json
{ "type": "confirm_requested", "t": 150.0, "turn_id": 2,
  "reason": "停顿明显变长", "used": 1, "budget": 5 }
```

```json
{ "type": "confirm_result", "t": 230.0, "turn_id": 3,
  "confirmed": false, "load_z": 0.16, "quality": 0.5 }
```

**建议做法**：提示区占位显示 `正在取证…（1/5）` → 收到 `hint` 就替换成提示卡；
收到 `confirm_result{confirmed:false}` 就改成灰色的 **「未证实」**。

> `confirmed:false` 一定要显示出来。**"没坐实"是产品可信度的来源**，
> 藏起来等于告诉评委你只会报喜。

## 6. `status` —— 降级与未授权

```json
{ "type": "status", "state": "no_consent",  "reason": "候选人未授权视频分析，本次仅语音", "t": 12.0 }
{ "type": "status", "state": "degraded",    "reason": "vision_api_error", "t": 40.0 }
{ "type": "status", "state": "degraded",    "reason": "上一段视频还在分析，本段已跳过", "t": 60.0 }
```

| state | 界面表现 |
|---|---|
| `no_consent` | 顶部蓝条「本次仅语音，不做画面分析」+ 信号带隐藏 |
| `degraded` | 顶部黄条 + 信号带变灰条纹，**不要清空已有画面** |
| `no_session` | 还没候选人进来就点了结束：提示「本场未开始」，回等待页 |

## 7. `snapshot` —— 刷新恢复

面试官手滑刷新是整个 demo 最容易崩的地方。连上后立刻会收到：

```json
{ "type": "snapshot", "session_id": "8d1711e2ba4a", "status": "live",
  "baseline_ready": true, "turns": 3,
  "candidate_online": true, "interviewer_online": true,
  "hints": [ { "id":"17eaa97d","turn_id":2,"kind":"probe",
               "text":"追问：当时谁反对","why":"…","t":150.0,
               "action":"used" } ],
  "adopt_rate": 0.75 }
```

拿到就**重放一遍**已发生的提示卡（`action` 非空的那几张要显示成已处理状态）。

## 8. 结束与报告

发 `{"type":"end"}` → 收到 `report_ready`：

```json
{ "type": "report_ready", "session_id": "8d1711e2ba4a",
  "report": {
    "title": "面试质量报告",
    "summary": "本场有 3 个点值得二追。",
    "points": [
      { "t": 150.0, "clock": "02:30", "label": "有东西没说透",
        "text": "追问：当时谁反对", "why": "负荷 +6.5σ，且停顿明显变长",
        "adopted": true, "hint_id": "17eaa97d" }
    ],
    "verification": { "requested": 4, "confirmed": 3, "unconfirmed": 1 },
    "hint_stats": { "total": 5, "used": 4, "ignored": 1, "adopt_rate": 0.8 },
    "disclaimer": "本报告不包含对候选人的任何评分或排序。"
  } }
```

报告页也可以直接拉 REST：`GET /api/sessions/{sid}/report?role=interviewer`。

⚠️ 报告里**不许出现任何 score / rank 字段**，`disclaimer` 必须原样显示。
`verification` 建议也显示出来：**"取证 4 次，坐实 3 次"** 比只报成功更能说明这套信号可验证。

## 9. REST 接口一览

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/rooms` | 创建房间，body `{job_title, questions?}` → `{code}` |
| GET | `/api/rooms/{code}` | 等待页轮询：`status`、对端是否在线 |
| POST | `/api/rooms/{code}/end` | 结束（WS 之外的兜底） |
| GET | `/api/interviews` | **场次**列表（不是候选人排名）。`duration` 是秒数浮点，`is_live=true` 表示还在进行中 |
| GET | `/api/sessions/{sid}/report?role=` | 报告，`role=candidate` 是另一套文案 |
| POST | `/api/hints/{id}/feedback` | WS 断线时的兜底，body `{action}` |
| GET | `/api/config` | 基线时长、阈值，用于渲染「建立基线中」 |
| GET | `/healthz` | 健康检查 |

## 10. 候选人侧（如果也归你做）

候选人连 `?role=candidate&consent=1`，然后**只做一件事**：监听 `record_request`，录 `seconds` 秒，发 `video_chunk`。

```json
// 收到
{ "type": "record_request", "t": 150.0, "seconds": 20,
  "turn_id": 2, "reason": "停顿明显变长" }

// 发回
{ "type": "video_chunk", "t": 170.0, "data": "<base64>", "ct": "video/webm" }
```

两个硬要求：
- **必须用 `stop()` → `start()` 循环切片，不能用 `timeSlice`**，否则第 2 段起无法独立解码。
- 分辨率 640×480、码率 800kbps（≈3MB/20s），低于接口 5MB 跳过阈值。

参考实现：`static/dev_recorder.html`。

> 候选人侧**永远不要显示任何 signal / hint**。他知道自己被实时分析，基线就被污染了。

## 11. 常见坑（都踩过）

1. **`signal` 没收到** —— 候选人没连、或 `consent=0`、或基线还没建好。先看 `hello_ack` 的 `session_id` 有没有。
2. **一直"建立基线中"** —— 视频形态下 `BASELINE_MIN_SAMPLES` 要设成 2~3，设成 8 永远不满足。
3. **一条提示都不出** —— 先查 `quality`。真实视频 sqi 只有 0.2 上下，`MIN_QUALITY` 必须 ≤0.15。
4. **提示要等半分钟才出现** —— 这是设计如此（录 20s + 处理 9~17s）。界面要给"正在取证"的中间态。
5. **刷新后页面空白** —— 没处理 `snapshot`。
6. **CORS 报错** —— 后端已全开，确认你请求的是 `127.0.0.1:8000` 不是 `localhost:8000`（WebSocket 尤其容易混）。
7. **mock 模式下发 `video_chunk` 报错** —— 必须确保 `MockProvider` 有 `sample_video()`。
   没有的话后端会抛 `AttributeError` → 面试官端降级黄条。
   已有测试钉住（`TestMockVideoPath`），改 `vision.py` 时别把这个方法删了。
8. **改了后端代码但没生效** —— uvicorn 没加 `--reload`，改完必须重启进程。
9. **演示轮次自己触发消费** —— 前端第 2 轮写死了 `pause_ratio: 0.8`，
   在 `VISION_PROVIDER=facephys` 下会真的调一次 FacePhys（约 17.5 万 token）。
   现在默认只在 mock 模式跑，真机要手动加 `?scripted=1`。

## 12. 联调顺序（建议照这个走）

1. `POST /api/rooms` 拿到 code，确认房间创建 OK。
2. 用 `/` 自测台跑一遍，确认后端本身没问题。
3. 你连 `?role=interviewer`，看能不能收到 `hello_ack` + `snapshot`。
4. 再接上候选人侧（或直接用 `/recorder`），看 `signal` 能不能到。
5. 最后接 `hint` 的 UI —— 用 `/recorder` 配合，把「停顿占比」调高就能稳定触发取证。
